# 핵심 개념

ddoc 를 이해하는 데 필요한 개념들을 정리합니다.

## 1. 판정 (Verdict)

`ddoc diff` 는 두 데이터셋을 비교해 세 가지 중 하나로 답합니다.

| 판정 | exit code | 의미 |
|---|:---:|---|
| `OK` | 0 | 의미 있는 분포 변화가 없음 |
| `DRIFT` | 1 | 분포가 변했음 |
| `BLIND` | 2 | 판정할 근거가 없음 (경로 없음, 처리할 엔진 없음, 비교 실패 등) |

`BLIND` 는 "괜찮다" 가 아니라 "모른다" 입니다. 확인할 수 없는 상황을
`OK` 로 덮지 않기 위해 셋째 답을 둡니다.

`DRIFT` 는 다음 중 하나일 때 내려집니다.

- 전체 점수 `overall_score` 가 `--threshold` (기본 0.15) 이상
- 속성 하나의 점수가 `--attr-threshold` (기본 0.25) 이상 —
  평균에 묻히는 강한 국소 변화를 놓치지 않기 위함

severity 는 `high` / `medium` / `low` / `none` 으로 함께 표시됩니다.

## 2. Modality 와 자동 감지

입력 경로를 보고 데이터 종류(modality)를 추정합니다.
이미지 폴더는 `vision`, CSV 는 `csv`, ddoc categorical 레이아웃은
`categorical` 하는 식입니다. 생 CSV 는 내장 비교기로 처리되어 플러그인이
없어도 판정이 나옵니다.

플러그인이 읽는 dataset layout 은 modality 별 `ddoc.yaml` + 데이터 파일
입니다. 자세한 형식은 [toy 데이터 튜토리얼](toy-data.md) 의
`ddoc.yaml 컨벤션` 참고.

## 3. 플러그인과 검출기

ddoc 코어는 가볍고, 실제 분석은 플러그인이 합니다. 플러그인은
[pluggy](https://pluggy.readthedocs.io/) hookspec 을 구현하는 독립 pip
패키지이며 `ddoc` entry-point group 으로 등록됩니다.

주요 hookspec:

| hook | 역할 |
|---|---|
| `drift_detect` | 두 데이터의 drift 점수 계산 |
| `eda_run` | 한 데이터의 탐색적 분석 |
| `ddoc_supported_detectors` | 플러그인이 제공하는 검출기 목록 광고 |
| `report_render` | 결과를 리포트로 렌더 (없으면 내장 렌더러 사용) |
| `export_drift_report` | 결과를 외부 시스템으로 전송 (없으면 내장 file / http 사용) |
| `data_source_read` | 외부 데이터 소스 읽기 (없으면 내장 file 사용) |

`--detector` 로 검출 전략을 고릅니다 (`ddoc plugin detectors` 로 목록 확인).
한 플러그인이 입력을 처리하지 못해 실패해도 다른 플러그인의 결과는
그대로 사용됩니다.

## 4. Envelope

`--json` 출력과 명령 사이의 주고받기는 JSON envelope 한 객체로 합니다.
대표적인 필드는 `status`, `modality`, `overall_score`, `attribute_drifts`
입니다. `ddoc report render` 와 `ddoc export drift-report` 가 이
envelope 를 입력으로 받으므로, 단계별 결과를 파일로 남겨 다음 단계에
넘길 수 있습니다.

## 5. 진단서와 진단

`ddoc diff --report note.html` 은 판정을 검사 보고서 형식의 진단서(단일 HTML
파일, 오프라인·인쇄 가능)로 씁니다. 머리글에 발행처(`--issuer` 또는
`DDOC_ISSUER`), 문서 번호, 발행 일시가 들어가고, 데이터 유형·방법·기준·결과 표
뒤에 다음 섹션이 이어집니다.

| 섹션 | 내용 |
|---|---|
| 검사 대상 | 무엇과 무엇을 비교했는지 — 기준/현재의 경로, 규모(행×열), 기간(날짜·시간 열에서), 열 구성과 유형, 열 대조(공통 열, 한쪽에만 있는 열, 비교에서 뺀 날짜·시간 열과 누적·순번 열). `--sample-rows N` 을 주면 양쪽 앞 N행 |
| 요약 | 판정, 전체 점수(기준선이 표시된 미터), 기준 이상 속성 수, 표본 수 |
| 유형 판독 | 측정값을 미리 정리해 둔 드리프트 유형의 조건에 대어 본 결과 카드 — 신호(이 데이터의 수치), 이런 뜻일 때가 많다, 흔한 원인, 먼저 할 일, 주의. 요약 맨 위에 "판독: …" 한 줄 |
| 데이터 도면 | 열(속성) 하나를 부품 하나로, 데이터의 열 순서대로 그린 도면. 부품마다 기준/현재 썸네일과 판정(적합·주의·부적합)이 있고, 날짜·시간 열, 누적·순번 열, 한쪽에만 있는 열은 빗금으로 "비교 제외"를 표시. 살펴볼 부품에는 번호가 붙고, 아래 설명 목록이 같은 번호로 측정값을 보여줌. 부품이나 설명을 누르면 해당 속성 상세로 이동 |
| 판정 근거 | 어떤 규칙이 판정을 만들었는지 (예: 속성 하나가 단일 속성 기준을 넘음), 그 아래 계통별 검사표 |
| ↳ 계통별 검사표 | 구성·표본·분포·완전성·수치 범위·범주 구성 계통별로 항목마다 측정값, 기준, 판정(적합 / 주의 / 부적합) |
| 속성별 결과 | 속성별 점수 막대와 두 기준선. 기준 이상 속성만 강조색 |
| 속성별 상세 | 점수 상위 5개와 도면에 번호가 붙은 속성마다 한 줄 요약·패턴과 그래프 — 범주형은 값별 기준→현재 비중, 수치형은 두 분포와 중앙값 (1–5 점수처럼 값이 몇 개뿐인 정수 열은 값별 막대) |
| 원본 데이터 특징 | 열별 결측률·평균·표준편차·범위와 특이사항 (CSV) |
| 점검 항목 | 판정을 이끈 속성의 패턴에 맞춘 체크리스트 |
| 한계 및 비고 | 분포 비교의 한계 — 모델 성능 영향은 라벨 있는 표본으로 측정 |

그래프마다 "표로 보기"가 있고, 마우스를 올리거나 키보드로 초점을 옮기면 값이
표시됩니다. 오른쪽 위의 화면 버튼으로 자동(운영체제 설정)·주간·야간을 고를 수
있고(브라우저에 기억됨), "인쇄 / PDF" 버튼은 테마와 상관없이 흰 바탕 A4 로
인쇄합니다.

진단서와 `ddoc serve` 진단 화면의 표지는 하나에 뜻이 하나입니다.

| 표지 | 뜻 | 쓰이는 곳 |
|---|---|---|
| 낫표 「 」 (두 모서리) | 살펴볼 판독 | 유형 판독 카드, 진단 화면의 판정 (색은 판정 상태) |
| ※ | 판정을 얼마나 믿을지에 대한 메모 | 표본이 적을 때 등의 주의, 표본 행 안내 |
| 빗금 | 비교 제외 | 데이터 도면의 날짜·시간 열, 누적·순번 열, 한쪽에만 있는 열 |
| 점선 | 한쪽에만 있음, 또는 가까움 | 검사 대상의 열 구성, 유형 판독의 "가까움" |

감지하는 패턴: 새 값 등장, 값 소멸, 구성비 변화(10%p 이상), 기준 범위 밖 값(5%
이상), 평균 이동(기준 표준편차의 0.5배 이상), 산포 변화(1.5배 이상), 결측률
변화(5%p 이상). 어느 쪽이든 표본이 30개 미만이면 잠정 판정으로 경고합니다.

계통별 검사표에서 **부적합**은 판정을 만든 항목(기준을 넘은 점수)이고, **주의**는
위 패턴이 기준을 넘은 항목입니다. 주의는 그 자체로 판정을 바꾸지 않습니다. 예를
들어 1–5 점수의 평균이 크게 움직였는데 분포 점수가 기준 아래라면, 판정은 OK 이지만
검사표에는 "평균 이동 — 주의"로 남습니다. 한쪽에만 있는 열은 비교할 수 없으므로
"열 일치 — 주의"가 되고, 기준에만 있던 열은 판정과 상관없이 점검 항목에 올라갑니다.

큰 CSV 는 한쪽이 20만 행(`--max-rows`)을 넘으면 파일을 조각으로 읽으며 균등 무작위 표본을 뽑아
비교합니다. 메모리는 표본 크기만큼만 쓰고, 같은 데이터는 늘 같은 표본이 됩니다. 진단서의 규모 줄에
"2,000,000행 중 200,000행 무작위 추출"처럼 표시되고, JSON 의 `raw.profile.<side>.total_rows` 에 전체
행 수가 남습니다. 쪽마다 200만 행으로 해 본 결과 점수 차이는 0.001 이내였습니다.

날짜·시간 열은 기간을 표시하는 데 쓰고 비교하지 않습니다. 텍스트 열 가운데 이름이
`date`·`time`·`_at` 등이거나, 이름과 상관없이 값의 90% 이상이 날짜 모양(연도 네 자리가 있는
`2026-07-01`, `2026/07/01`, `07/01/2026`, ISO 시각)인 열이 해당하며, 어느 쪽이든 값의 90% 이상이 실제로
날짜로 읽혀야 합니다.
서로 다른 기간의 타임스탬프는 늘 다르기 때문에, 비교하면 항상 드리프트로 나오기 때문입니다. 정수 인덱스처럼 숫자로 된
`timestamp` 열은 지금처럼 수치형으로 비교합니다.

### 임베딩 지도

이미지·텍스트 플러그인이 임베딩까지 비교하면(`ddoc diff --with-embeddings`, 모델을
불러오므로 느림) 진단서에 **임베딩 지도**가 들어갑니다. 두 데이터의 임베딩을 함께 PCA 로
2차원에 투영한 산점도(기준 회색, 현재 파랑, 각 중심 표시)와 두 수치입니다.

- **중심 이동** — 현재 중심이 기준 퍼짐의 몇 배만큼 움직였는지. 기준 항목이 한 점에
  모여 있으면(예: 같은 이미지) 계산하지 않습니다.
- **이웃 섞임** — 현재 항목의 가까운 이웃(원래 임베딩 공간에서) 가운데 기준 항목의
  비율을, 두 데이터가 한 집단일 때의 기대값으로 나눈 값. 1 = 고르게 섞임, 0 = 완전히 분리.

지도 아래에는 **열어서 볼 항목**을 파일 이름으로 보여줍니다: 기준의 대표 항목(기준 중심에
가장 가까운 것), 현재의 대표 항목, 기준과 가장 다른 현재 항목(가장 가까운 기준 항목과도 먼 것).
무엇이 달라졌는지는 마지막 목록이 가장 잘 보여줍니다.

한쪽 항목이 20개 미만이면 지도와 수치가 불안정하다고 표시합니다. 같은 값이 JSON 의
`raw.embedding_projection` 에 있고, 플러그인은 `ddoc.embedding.project(ref, cur)` 로 만듭니다
(numpy 만 사용).

### 유형 판독

드리프트는 반복되는 모양으로 나타납니다. ddoc 은 이런 유형들을 미리 글로 정리해 두고
(`ddoc/archetypes.py`), 측정값이 각 유형의 조건을 채우는지 봅니다. 조건을 모두 채우면
**해당**, 하나만 근소하게 모자라면 **가까움**(조기 신호)입니다.
유형 설명은 일반론이며, 이 데이터에 대한 결론은 아닙니다. 카드의 "먼저 할 일"은
원인을 확인하거나 배제하는 방법입니다. 카드 아래의 "판단 기준"이 아래 표와 같은 문장입니다.

더 구체적인 유형이 해당하면 그것이 설명하는 일반 유형은 숨깁니다. 예를 들어 단위
변경형이 해당하면 수준 이동형과 산포 변화형은 따로 나오지 않습니다. 유형마다 변화 하나만 심은
[판독 드릴](../../zoo/README.md#판독-드릴)이 있어, 각 유형이 정답대로 읽히는지(빠지거나 더 나오지
않는지, 어느 열에서 나오는지)를 `./run.sh zoo` 와 테스트가 확인합니다.

같은 진단은 `--json` 출력의 `diagnosis` 필드에 언어와 무관한 코드와 수치로
실리므로, 애플리케이션이 코드(`new_values`, `out_of_range` 등)를 기준으로
처리할 수 있습니다. 유형 판독은 `diagnosis.archetypes`, 계통별 검사표는 `diagnosis.inspection`, 검사 대상 정보는
`raw.profile` 에 있습니다.

## 6. 분석 캐시

플러그인은 같은 데이터를 다시 분석하지 않도록 분석 결과를 캐시에
저장합니다. `ddoc analyze eda --invalidate-cache` 로 캐시를 무시하고
다시 분석할 수 있습니다.

## 7. 레시피

fetch → analyze → report → export 같은 여러 단계를 YAML 파일 하나에
적고 `ddoc recipe run <file>` 로 실행합니다. 변수 치환을 지원하므로
drift 점검 파이프라인 전체가 리뷰 가능한 텍스트가 됩니다.
자세한 내용은 [레시피 튜토리얼](recipe.md).
