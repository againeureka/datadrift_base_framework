# dashcam — 실제 블랙박스 주행의 프레임

2채널 블랙박스로 찍은 **실제 주행 12분**의 프레임입니다. ddoc 은 동영상을 직접 비교하지 않습니다. 몇 초마다
프레임을 뽑아 이미지 폴더 둘로 비교합니다. 판정은 vision 플러그인이 맡습니다(`./run.sh setup vision`, torch 필요).

```bash
python make.py                    # 다른 카메라 (기본) → data/ref/, data/cur/
ddoc diff data/ref data/cur --with-embeddings --lang ko --report note.html
ddoc examples tour dashcam        # 아래 이야기 넷을 한 단계씩 (투어)
```

데이터는 패키지에 들어 있어(`ddoc/examples/data/dashcam.zip`, 2MB) 따로 내려받지 않습니다. `ddoc serve` 첫 화면의
예제 사례 중 세 개(다른 카메라 · 다음 구간 · 렌즈 흐림)도 같은 프레임을 씁니다.

## 데이터

| 묶음 | 프레임 | 간격 |
|---|---|---|
| 전방 카메라, 주행 앞 6분 | 121 | 3초 |
| 전방 카메라, 주행 뒤 6분 | 60 | 6초 |
| 후방 카메라(뒷유리 너머), 주행 앞 6분 | 61 | 6초 |

- 원본은 1080p 전방(30fps)·후방(2fps) 영상과 GPS·가속도 기록이 섞인 블랙박스 파일입니다. 영상 두 줄만 읽고
  GPS·센서 기록은 풀지 않았습니다.
- 프레임마다 위쪽 840줄만 남겨(대시보드, 화면에 찍힌 날짜·시각·속도, 대시보드의 물건이 잘려 나감) 320 × 140
  으로 줄였고, 메타데이터 없이 JPEG 으로 저장했습니다. 이 크기에서는 번호판과 얼굴을 읽을 수 없습니다.
- 파일 이름은 시각이 아니라 주행 시작부터의 초입니다(`front-t0012.jpg` = 12초).
- 원본에서 이 파일을 만드는 과정은 [prepare.py](prepare.py)에 있습니다(원본은 저장소에 없음, ffmpeg 필요).
- 데이터는 저장소와 같은 Apache-2.0 라이선스를 따릅니다.

## 이야기와 결과

`--with-embeddings` 로 비교한 결과입니다. 기준은 모두 전방 카메라의 앞 6분(6초 간격, 61장)입니다.
**이웃 섞임**은 임베딩 지도에서 두 묶음이 섞인 정도로, 1이면 고르게 섞였고 0이면 완전히 갈라졌습니다.

| story | 현재 | 판정 (점수) | 가장 변한 속성 | 이웃 섞임 | 속성 판독 |
|---|---|---|---|---|---|
| `camera-swap` | 후방 카메라, 같은 순간 | **DRIFT** (0.528) | 노출 0.976 · 색감 0.958 · 임베딩 분리 0.857 | 0.14 | 노출·명암 범위 이동·확산형 · 색감 이동·수축형 · 밝기·잡음·엔트로피 수준 이동형 |
| `next-stretch` | 전방, 뒤 6분 | **DRIFT** (0.301) | 임베딩 분리 0.784 · 엔트로피 0.586 · 선명도 0.569 | 0.22 | 엔트로피·색감 산포 변화형 · 선명도 수준 이동형 |
| `same-stretch` | 전방, 같은 구간의 3초 뒤 프레임 | OK (0.000) | — | 1.00 | 안정형 |
| `blurry-lens` | 위 + 렌즈 흐림 | **DRIFT** (0.491) | 명암 범위 1.000 · 잡음 1.000 · 임베딩 분리 1.000 | 0.00 | **선명도·잡음 이동·수축형** · 명암 범위·노출 이동·확산형 |
| `low-quality` | 위 + 절반 해상도·강한 압축 | **DRIFT** (0.390) | 잡음 1.000 · 임베딩 분리 1.000 · 선명도 0.800 | 0.00 | **잡음·선명도 이동·수축형** · 엔트로피 수준 이동형 · 명암 범위 이동·확산형 |
| `overexposed` | 위 + 밝기 ×1.6 | **DRIFT** (0.408) | 노출 0.992 · 밝기 0.924 · 엔트로피 0.807 | 0.20 | **밝기·엔트로피 수준 이동형** · 노출 이동·확산형 |

같은 구간을 빼면 이야기마다 데이터 전체 판독(임베딩 분리형 · 레짐 전환형)이 함께 나옵니다. vision 플러그인이
이미지마다 잰 속성값을 넘기므로, ddoc 은 CSV 의 수치 열과 같은 방식으로 속성마다 점수(JS 거리, 표본 잡음으로
설명되면 0)를 매기고 변화의 모양을 읽으며 진단서에 기준·현재 분포 그래프를 그립니다. 임베딩 지도는
`embedding_separation`(임베딩 분리 = 1 − 이웃 섞임)으로 한 속성이 됩니다.

**다른 카메라 (`camera-swap`).** 같은 순간을 찍은 전방과 후방 프레임입니다. 후방은 뒷유리 너머라 붉고 보랏빛이
돌며, 뒤따르는 차와 길가의 단풍이 보입니다. 전방 영상으로 학습한 모델에 후방 영상이 잘못 들어온 상황이고,
노출과 색감이 가장 크게 바뀌며 지도에서 두 묶음이 갈라집니다. 진단서의 지도 아래에 열어 볼 프레임(각 쪽의
대표 프레임, 기준과 가장 다른 현재 프레임)이 나옵니다.

**다음 구간 (`next-stretch`).** 카메라는 같고 고장도 없지만 DRIFT 입니다. 앞 6분은 고가도로와 트인 하늘, 뒤
6분은 시내 도로가 많습니다. 풍경이 바뀐 것이고, 기준 데이터가 앞으로 만날 도로·시간대·날씨를 덮어야 한다는
뜻입니다.

**심은 변화 (`blurry-lens`, `low-quality`, `overexposed`).** 같은 구간의 3초 뒤 프레임에 변화 하나씩을 심어
정답을 압니다. 흐림은 선명도·잡음·명암 범위, 화질 저하는 잡음·선명도, 노출은 노출·밝기가 가장 크게
움직이고, 바뀐 것이 없는 같은 구간(0점)과 분명히 갈립니다. 흐림과 화질 저하에서 선명도가 **이동·수축형**으로
읽히는 것은 세부가 지워진 프레임들이 낮은 선명도 근처로 몰리기 때문입니다.

**같은 구간 (`same-stretch`).** 바뀐 것이 없는 3초 뒤 프레임입니다. 쪽마다 60장이면 우연만으로도 속성 분포가
조금씩 다르지만, 그 차이는 잡음 검정을 넘지 못해 모든 점수가 0 이고, 판정은 OK, 판독은 안정형입니다. 임베딩
지도도 완전히 섞입니다(1.00). 우연이 벌려 놓은 거리는 작지 않아서(선명도·잡음 수준 0.36 정도), 콘솔의 "잡음 범위
안" 줄과 진단서의 점선 막대가 그것을 보여 줍니다. 60장으로는 이 정도 차이를 변화라 말할 수 없다는 뜻입니다.


## 내 영상으로

```bash
ffmpeg -i before.mp4 -vf fps=1/3,scale=320:-1 ref/%04d.jpg    # 3초마다 한 장
ffmpeg -i after.mp4  -vf fps=1/3,scale=320:-1 cur/%04d.jpg
ddoc diff ref cur --with-embeddings --report note.html
```

화면에 시각·속도 같은 글자가 찍힌 영상이면 `crop` 으로 그 줄을 잘라내세요(`-vf crop=iw:ih*0.78:0:0,fps=1/3,…`).
글자도 이미지의 일부라 비교에 섞입니다.
